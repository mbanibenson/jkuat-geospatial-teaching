How to use this reader

This is a build unit. By week 11 you will have deployed a working application, at a public URL, backed by a spatial database, that someone other than you can use. Everything in the reader is arranged toward that.

Each chapter covers one week and has the same parts: learning outcomes, the reading, a two-tier practical, self-test questions, and further reading. The Core practical is what everyone completes; the Extension is for those who finish early.

This unit is in two languages you have not used

Your programming unit was Python. This unit is JavaScript and SQL. Nothing about that is beyond you — but do not assume the transfer is automatic, because the two most common ways to struggle here are treating JavaScript as though it were Python, and treating SQL as though it were a programming language rather than a declarative one.

Work through Appendix A before week 2. It is a self-check, not a test, and it will tell you privately which of the two you need to spend a weekend on.

One habit to form now: keep the browser developer tools open at all times. Not when something breaks — always. The Network tab shows you every request your map makes, its size and its timing; the Console shows you the errors that would otherwise present as a silent blank grey box. Students who work with devtools open debug in minutes what students who do not debug in hours. This is the single highest-value habit in the unit.

Anatomy of a web map

By the end of this week you should be able to

  • Explain the tile pyramid and compute the tile index for a given point and zoom
  • Say what Web Mercator distorts, by how much, and where it does not matter
  • Distinguish raster tiles, vector tiles and GeoJSON, and say when each is appropriate
  • Read a map's network traffic in developer tools

What actually happens

You open a web map centred on Nairobi. In the second before it appears, this happens:

  1. The browser requests an HTML page. That page loads the Leaflet CSS and JavaScript.
  2. Leaflet creates a <div> and works out which geographic area it must cover at the requested zoom.
  3. It calculates which tiles — small fixed square images, conventionally 256 × 256 pixels — cover that area, typically nine to twenty of them.
  4. It issues one HTTP request per tile, in parallel, to a tile server.
  5. Each tile arrives as a PNG and is positioned absolutely inside the div by CSS.
  6. Your own data — points, boundaries — arrives separately as GeoJSON and is drawn as SVG or canvas on top.

The whole design rests on one decision: pre-render the base map once, into fixed tiles, and serve them as static images. Nothing is computed per user. A tile is just a file, so it caches in the browser, in the CDN, and at every proxy in between. This is why a web map can serve millions of users on modest infrastructure, and it is why the "slippy map" replaced the older approach of asking a server to render a fresh image for every pan.

The tile pyramid

A tile is addressed by three numbers: z (zoom), x (column, west to east) and y (row, north to south — the origin is the top-left corner, which surprises people used to y increasing northward). A tile URL is a template with those three slots:

https://tile.openstreetmap.org/{z}/{x}/{y}.png

The conversion from longitude and latitude to tile indices is:

x = ⌊ λ + 180360 · 2z ⌋ y = ⌊ 1 − asinh(tan φ) / π2 · 2z ⌋

λ is longitude and φ latitude in radians. The asinh term is the Mercator projection of latitude; everything peculiar about web maps traces back to it.

Worked example — which tile is Nairobi in?

Nairobi city centre: λ = 36.8219°E, φ = −1.2921°. Take zoom 12, so 212 = 4096.

Column. (36.8219 + 180) / 360 = 216.8219 / 360 = 0.602283. Multiply by 4096 → 2466.95, floor → x = 2466.

Row. φ = −1.2921° = −0.022551 rad. tan φ = −0.0225548. asinh(tan φ) = ln(−0.0225548 + 1.0002544) = ln(0.9776996) = −0.0225528.
(1 − (−0.0225528)/π) / 2 = (1 + 0.0071785) / 2 = 0.5035893. Multiply by 4096 → 2062.70, floor → y = 2062.

So Nairobi at zoom 12 is tile 12/2466/2062. Paste https://tile.openstreetmap.org/12/2466/2062.png into your browser and you will get a 256-pixel image of central Nairobi. Do this before the lecture. A web map is a great deal less mysterious once you have fetched a tile by hand.

Web Mercator, and where it lies

Almost every web map uses EPSG:3857, "Web Mercator". It was chosen for one practical reason: Mercator is conformal, so shapes and angles are locally correct and north is always up, which makes tiles that stitch seamlessly and pan intuitively. The price is area. Mercator inflates area by a factor of sec²φ — that is, 1/cos²(latitude).

LatitudeArea inflationWhere
0°×1.00Nairobi, Kampala, Kisumu
30°×1.33Cairo
45°×2.00Milan
60°×4.00Oslo, Anchorage
75°×14.9Northern Greenland

This is the source of the familiar Greenland problem. Greenland's true area is about 2.17 million km²; the Democratic Republic of the Congo's is about 2.34 million km². The DRC is genuinely the larger country. On a Web Mercator map Greenland appears roughly fourteen times bigger.

There is a local point worth noticing here. Kenya sits on the equator, so Web Mercator distortion across Kenya is negligible — at 1.3° the inflation factor is 1.0005, five parts in ten thousand. For a map of Nairobi County you may reason about Web Mercator areas without much guilt. For a map of Africa, or of the world, you may not. Knowing which situation you are in is the professional skill; assuming one or the other is how errors happen.

Never compute area or distance in Web Mercator

Even where the distortion is small it is not zero, and the habit is what matters. A Web Mercator area is in metres that are not real metres, and the scale factor varies across your map. Project to an equal-area or a local projection first — for Kenya, UTM zone 36S (EPSG:32736) or 37S (EPSG:32737). Week 5 shows the SQL version of this mistake, which is even easier to make and even harder to see.

Standards, and why they exist

The Open Geospatial Consortium publishes the specifications that let software from different vendors interoperate. WMS returns a rendered image; WFS returns actual features; WMTS returns tiles. All are covered in week 7. Their value is concrete: a county publishing a WMS endpoint can be consumed in QGIS, ArcGIS, Leaflet and OpenLayers with no bespoke work by anyone. Standards are what stop every dataset needing its own client.

JavaScript for people who know Python

The syntax is learnable in an afternoon. What causes trouble is the handful of places where JavaScript behaves differently from what your Python instincts predict.

The last row is the one that matters, and it is not a syntax difference — it is a difference in how the language runs. Python executes a line, waits for it to finish, moves on. JavaScript in the browser must never wait, because waiting would freeze the page. So an operation that takes time — fetching a file over the network — returns immediately with a promise of a future result, and your code says what to do when it arrives.

The bug every student writes in week 3

You fetch some GeoJSON, then on the next line try to use it, and it is undefined. Nothing is broken: the fetch has not finished. Your next line ran immediately, because JavaScript did not wait.

The fix is to put the work inside the response handler — either .then(data => { ... }) or by marking the function async and writing await. Once you have seen this once and understood it, you have understood asynchrony, and most of what makes browser JavaScript feel strange goes away.

JavaScript 
// WRONG — data is undefined, because fetch has not finished
let data;
fetch("facilities.geojson").then(r => r.json()).then(d => { data = d; });
console.log(data.features.length);          // TypeError

// RIGHT — do the work inside the handler
fetch("facilities.geojson")
  .then(r => {
    if (!r.ok) throw new Error(`HTTP ${r.status}`);   // fetch does NOT throw on 404
    return r.json();
  })
  .then(data => { console.log(data.features.length); })
  .catch(err => console.error("failed to load:", err));

// RIGHT — the same thing, more readable
async function load() {
  const r = await fetch("facilities.geojson");
  if (!r.ok) throw new Error(`HTTP ${r.status}`);
  const data = await r.json();
  console.log(data.features.length);
}

HTTP, in the amount you need

Every piece of data on your map arrives through an HTTP request. Four things to know:

  • Methods. GET retrieves and must not change anything. POST creates. PUT replaces, PATCH modifies, DELETE removes. Week 8 uses all of them.
  • Status codes. 200 fine; 301/302 moved; 400 your request was malformed; 401 not authenticated; 403 authenticated but not allowed; 404 not found; 500 the server broke. The distinction between 401 and 403, and between 400 and 500, tells you which side of the wire to debug.
  • Headers. Metadata on both sides. Content-Type says what the body is; the CORS headers decide whether your JavaScript is allowed to read the response.
  • CORS. By default, JavaScript on your page may not read a response from a different origin. The server must opt in with an Access-Control-Allow-Origin header. You will meet this in week 7 with GeoServer, and it is the most common cause of a map that works locally and fails when deployed.

GeoJSON, properly

GeoJSON (RFC 7946) is the interchange format of the web mapping world. It is JSON with a specified structure.

GeoJSON 
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": {
        "type": "Point",
        "coordinates": [36.8219, -1.2921]        // [longitude, latitude] — in that order
      },
      "properties": {
        "name": "Kenyatta National Hospital",
        "level": 6,
        "beds": 1800
      }
    }
  ]
}

Seven rules that the specification actually imposes, and that people actually break:

  1. Coordinates are [longitude, latitude]. X before Y. This is the opposite of how you say it aloud and the opposite of Leaflet's own L.latLng.
  2. The CRS is always WGS84 (CRS84, equivalent to EPSG:4326). RFC 7946 removed the ability to declare any other. If your data is in UTM, transform it before writing GeoJSON — a file with UTM coordinates in it is not GeoJSON, whatever the extension says.
  3. Seven geometry types: Point, LineString, Polygon, MultiPoint, MultiLineString, MultiPolygon, GeometryCollection.
  4. Polygon rings must close — the last coordinate pair repeats the first.
  5. Ring winding order: exterior rings counter-clockwise, interior rings (holes) clockwise, by the right-hand rule.
  6. No comments, no trailing commas, no NaN. It is JSON, and JSON has none of these.
  7. A geometry may be null — a valid Feature with attributes and no location.
Longitude first. Except in Leaflet, where it is latitude first.

GeoJSON writes [36.8219, -1.2921]. Leaflet's L.marker and L.latLng take [-1.2921, 36.8219]. Both are internally consistent; the two conventions simply disagree, and you must hold both in your head.

The symptom of getting it wrong is unmistakable and worth memorising: your Kenyan data appears in the Indian Ocean off Somalia, because you have plotted (36.8°N, −1.3°E) instead of (1.3°S, 36.8°E). If a point lands in the sea, check the coordinate order before you check anything else. Note that L.geoJSON() does the swap for you automatically — so this bites specifically when you hand-build markers from parsed coordinates.

The smallest working map

Leaflet needs three things: a CSS file, a JavaScript file, and a <div> that has a height. The third catches everyone.

HTML 
<link rel="stylesheet"
      href="https://unpkg.com/leaflet@1.9.4/dist/leaflet.css">
<script src="https://unpkg.com/leaflet@1.9.4/dist/leaflet.js"></script>

<style>
  html, body { height: 100%; margin: 0; }
  #map { height: 100%; }        /* without a height, the map is invisible */
</style>

<div id="map"></div>

<script>
  // note the order: LATITUDE first in Leaflet
  const map = L.map("map").setView([-1.0996, 37.0134], 15);   // JKUAT main campus

  L.tileLayer("https://tile.openstreetmap.org/{z}/{x}/{y}.png", {
    maxZoom: 19,
    attribution: '&copy; <a href="https://www.openstreetmap.org/copyright">OpenStreetMap</a> contributors'
  }).addTo(map);
</script>
A blank grey box is almost always one of four things

The div has no height. Leaflet cannot infer one, and a div with no content is zero pixels tall. Give it an explicit height in CSS.
The script runs before the div exists. Put your script after the div, or wrap it in a load handler.
You opened the file with file://. Serve it over HTTP.
You forgot the Leaflet CSS. The map works, but every tile is stacked at the origin, which looks like chaos rather than a grey box.
Check the Console before you change anything. It usually names the problem outright.

Attribution is not optional

OpenStreetMap data is licensed under the ODbL, which requires attribution — the credit line in the corner is a licence condition, not decoration. Removing it is a licence breach. Some tile providers additionally cap usage: OSM's own tile servers are for development and low-volume use only, and a deployed application sending them significant traffic will be blocked. For anything real, use a provider with terms you have read — Carto, Stadia, MapTiler, or your own tile server. This comes up in week 10.

Markers, popups and tooltips

A marker is a point with an icon. A popup opens on click and holds arbitrary HTML. A tooltip appears on hover and should be short. The default marker icon is a blue pin; a custom icon needs its size and, critically, its anchor — the pixel within the image that sits on the geographic point. Get the anchor wrong and every marker is offset by half an icon, which looks fine on its own and is wrong everywhere.

JavaScript 
const clinicIcon = L.icon({
  iconUrl:     "icons/clinic.png",
  iconSize:    [32, 32],
  iconAnchor:  [16, 32],    // bottom centre — the tip of the pin
  popupAnchor: [0, -32]     // popup opens above the icon, not over it
});

L.marker([-1.0996, 37.0134], { icon: clinicIcon })
  .addTo(map)
  .bindPopup("<strong>JKUAT Health Centre</strong><br>Level 3 · Open 24 h")
  .bindTooltip("JKUAT Health Centre");

GeoJSON layers — where the real work happens

L.geoJSON() takes a FeatureCollection and turns it into a layer. It also handles the coordinate-order swap for you. Four options carry almost all of its power:

  • pointToLayer(feature, latlng) — decides what a Point becomes. Return an L.circleMarker instead of a pin and you can size and colour it by an attribute.
  • style(feature) — returns a style object for lines and polygons. Called once per feature, so it can depend on the data.
  • onEachFeature(feature, layer) — runs once per feature after creation. Bind popups and event handlers here.
  • filter(feature) — return false to drop a feature before it is drawn.
JavaScript 
const res = await fetch("facilities.geojson");
const data = await res.json();

const layer = L.geoJSON(data, {

  filter: f => f.properties.operational === true,

  pointToLayer: (f, latlng) => L.circleMarker(latlng, {
    radius: Math.sqrt(f.properties.beds) / 2,   // area ∝ beds, not radius ∝ beds
    fillColor: "#0E6E78",
    color: "#ffffff",
    weight: 1,
    fillOpacity: 0.75
  }),

  onEachFeature: (f, lyr) => {
    const p = f.properties;
    lyr.bindPopup(`<strong>${p.name}</strong><br>Level ${p.level} · ${p.beds} beds`);
    lyr.on("mouseover", e => e.target.setStyle({ weight: 3 }));
    lyr.on("mouseout",  e => e.target.setStyle({ weight: 1 }));
  }

}).addTo(map);

map.fitBounds(layer.getBounds(), { padding: [20, 20] });   // let the data set the view

Two details in that code are worth dwelling on. fitBounds lets the data decide the view rather than a hard-coded setView — so the map still works when the dataset changes. And the radius uses a square root: human perception reads circle area, so scaling the radius directly by the value makes a facility with four times the beds look sixteen times bigger. Getting this wrong is one of the most common quantitative errors in thematic mapping.

Counts are almost always the wrong variable

Start here, because it is the error that invalidates whole maps. A choropleth colours areas by a value. If that value is a raw count, the map shows you where the people are, not where the phenomenon is. A map of the absolute number of health facilities per county is, to a first approximation, a map of county population — and it will be read as a map of health provision, which is a different and false claim.

Normalise: facilities per 100,000 people, cases per 1,000, hectares per km². The choropleth is a map of intensity, and intensity requires a denominator. There is exactly one exception — mapping a total that genuinely is the quantity of interest, such as total budget allocated — and even then a proportional symbol is usually the better form.

Classification changes the message

Having chosen a variable, you must choose how to cut it into classes. This is not a technical detail; it determines what the reader concludes.

Worked example — the same data, two honest maps

Health facilities per 100,000 population, ten counties:

CountyManderaTurkanaKilifiMeruMachakosKisumuMombasaNakuruKiambuNairobi
Rate571217192122242834

Equal interval, 5 classes. Range 5–34, so class width 5.8:

5.0–10.8 → Mandera, Turkana (2)
10.8–16.6 → Kilifi (1)
16.6–22.4 → Meru, Machakos, Kisumu, Mombasa (4)
22.4–28.2 → Nakuru, Kiambu (2)
28.2–34.0 → Nairobi (1)

Quantile, 5 classes, two counties each:

Mandera, Turkana │ Kilifi, Meru │ Machakos, Kisumu │ Mombasa, Nakuru │ Kiambu, Nairobi

Read the difference. Under equal interval, four counties share the middle class — the centre of the distribution looks flat and homogeneous — and Nairobi stands alone at the top as a visible outlier, which is what the numbers actually say. Under quantile, every class holds exactly two counties, so the middle counties are spread across three shades and look far more differentiated than a 3-point spread warrants; Nairobi loses its distinctness by sharing a class with Kiambu.

Neither map is dishonest. They answer different questions: equal interval preserves the true numeric gaps, quantile guarantees visual contrast. What is dishonest is producing both, choosing the one that supports your preferred conclusion, and not saying so.

Colour

  • Sequential — light to dark in one hue, for ordered data from low to high.
  • Diverging — two hues meeting at a neutral midpoint, for data with a meaningful centre: change from a baseline, above and below a target.
  • Qualitative — distinct hues of similar lightness, for categories with no order. Land cover, ownership type. Never use a sequential ramp for categories; it implies an ordering that does not exist.

Use ColorBrewer rather than choosing colours by eye — the schemes are perceptually ordered and tested. Around 8% of men have a red–green colour vision deficiency, so a red-to-green diverging scheme is unreadable to roughly one in twelve of your male users; use ColorBrewer's colourblind-safe schemes, such as brown–blue-green or purple–green. And check your map in greyscale: if the classes are still distinguishable, lightness is doing the work and the map will survive both photocopying and colour blindness.

Five to seven classes is the practical maximum. Beyond that readers cannot match a polygon to a legend swatch reliably, and the extra precision is illusory.

Accessibility, briefly and seriously

A map built only for a mouse excludes people who navigate by keyboard, and a map whose only information channel is colour excludes people who cannot distinguish those colours. Three things cost you almost nothing:

Why not just serve files?

You have been loading GeoJSON files. For a static map of a few hundred features that is entirely correct. It stops working when any of the following becomes true, and in a real application all of them do:

  • The data changes, and several people change it — a file has no concurrency control, and two simultaneous writers lose each other's work.
  • You need a subset. Serving a 40 MB file so the browser can discard 39 MB of it is indefensible on a mobile connection.
  • You need a computed answer — facilities within 5 km of this point, the county containing this click. That is a query, not a file read.
  • You need transactions, backups, permissions, or an audit trail.

PostGIS extends PostgreSQL with spatial types, several hundred spatial functions, and spatial indexing. It is the standard open-source spatial database and the back end of a large share of the world's public-sector GIS.

Getting data in

  -nln counties -nlt PROMOTE_TO_MULTI \

  -nln facilities -oo X_POSSIBLE_NAMES=lon -oo Y_POSSIBLE_NAMES=lat \

Note -t_srs (transform to) against -a_srs (assign, without transforming). Use -a_srs only when the data is already in that CRS but is not labelled. Using it when the data is in a different CRS silently mislabels everything, and nothing will tell you.

Worked example — the square-degree disaster

Nairobi County has an area of roughly 696 km². Here is what three queries return.

SQL 
-- WRONG: geometry is in EPSG:4326, so this is SQUARE DEGREES
SELECT name, ST_Area(geom) FROM counties WHERE name = 'Nairobi';
--  Nairobi | 0.0565          ← a number, with no meaning

-- RIGHT: project to UTM 37S, divide to km²
SELECT name, ST_Area(ST_Transform(geom, 32737)) / 1e6 FROM counties
WHERE name = 'Nairobi';
--  Nairobi | 696.1           ← km²

-- ALSO RIGHT: cast to geography, which always works in metres
SELECT name, ST_Area(geom::geography) / 1e6 FROM counties
WHERE name = 'Nairobi';
--  Nairobi | 696.0

The first query does not fail. It returns a plausible-looking decimal number that a student will paste into a report. Distance behaves identically: ST_Distance between Nairobi and Mombasa in EPSG:4326 returns 3.96 — the Pythagorean distance in degrees — while the same query cast to geography returns 438,900 metres, which is the real answer.

This is the single most consequential error in spatial SQL, and it is invisible: no error, no warning, just a wrong number. Rule: if a query contains ST_Area, ST_Length, ST_Distance or ST_Buffer, it must also contain ST_Transform or ::geography. Make this automatic.

Indexes, and the difference they make

Without an index, a spatial query compares your search geometry against every row in the table. A GiST index stores each geometry's bounding box in a tree, so the database can eliminate most rows before doing any real geometric work.

SQL 
CREATE INDEX facilities_geom_idx ON facilities USING GIST (geom);
ANALYZE facilities;                -- update the planner's statistics

-- prove it worked: run this before and after creating the index
EXPLAIN ANALYZE
SELECT f.name
FROM facilities f JOIN counties c ON ST_Intersects(f.geom, c.geom)
WHERE c.name = 'Kiambu';
-- before: Seq Scan on facilities
-- after:  Index Scan using facilities_geom_idx
Two ways to accidentally disable your index

Wrapping the indexed column in a function. WHERE ST_Transform(geom, 32737) && box cannot use the index on geom, because the index knows nothing about the transformed values. Transform the other side of the comparison instead, or build a functional index.

Using ST_Distance(a, b) < 5000 instead of ST_DWithin(a, b, 5000). The first computes an exact distance for every row and then filters; the second uses the index to eliminate rows first. They return the same answer, and on a large table one takes milliseconds and the other takes minutes.

The architecture you are building

GeoJSON straight from SQL

PostGIS can assemble a complete FeatureCollection in the database, so your API becomes a thin pipe rather than a place where objects are laboriously rebuilt in Python.

SQL 
SELECT json_build_object(
  'type',     'FeatureCollection',
  'features', COALESCE(json_agg(feature), '[]'::json)   -- [] not null when empty
)
FROM (
  SELECT json_build_object(
    'type',       'Feature',
    'geometry',   ST_AsGeoJSON(geom)::json,
    'properties', json_build_object('id', id, 'name', name, 'beds', beds)
  ) AS feature
  FROM facilities
  WHERE geom && ST_MakeEnvelope(%s, %s, %s, %s, 4326)   -- bbox, index-aware
  LIMIT 5000
) f;

Two things there earn their place. COALESCE(..., '[]') means an empty result is a valid empty FeatureCollection rather than null, which would crash your JavaScript. And the && bounding-box operator uses the GiST index, so a request for the current map view touches only the rows in view — which is what makes the whole approach scale.

A minimal API

Python 
from flask import Flask, jsonify, request, abort
import psycopg2, psycopg2.extras

app = Flask(__name__)

@app.route("/api/facilities")
def facilities():
    try:
        bbox = [float(v) for v in request.args["bbox"].split(",")]
        assert len(bbox) == 4
    except (KeyError, ValueError, AssertionError):
        abort(400, "bbox required as minx,miny,maxx,maxy")

    with psycopg2.connect(DSN) as conn, conn.cursor() as cur:
        cur.execute(SQL, bbox)          # parameterised — NEVER f-string user input
        return jsonify(cur.fetchone()[0])
JavaScript

  const b = map.getBounds();
  const bbox = [b.getWest(), b.getSouth(), b.getEast(), b.getNorth()].join(",");
  const r = await fetch(`/api/facilities?bbox=${bbox}`);

Binding to moveend rather than move is the difference between one request per pan and several hundred. On a laboratory network you might not notice; on a phone you will.

Keeping payloads small

  • Select only the columns the map uses. A table has thirty attributes; the popup shows four. Sending thirty is thirty.
  • Filter by bounding box. Always.
  • Simplify by zoom. ST_Simplify with a tolerance scaled to the zoom level: national boundaries at zoom 6 do not need centimetre vertices. Use ST_SimplifyPreserveTopology for polygons, or adjacent counties will develop gaps between them.
  • Reduce coordinate precision. ST_AsGeoJSON(geom, 5) gives about one metre — plenty for a web map, and it can cut file size by a third against the fifteen decimal places PostGIS emits by default.
  • Cap the result. A LIMIT with an honest message beats a request that times out.

What GeoServer is for

Last week you wrote your own API. It works, and for a bespoke application it is often the right choice. But it is yours — nobody else's software knows how to talk to it. GeoServer instead speaks the OGC standards, which means that the moment you publish a layer, it can be consumed by QGIS, ArcGIS, OpenLayers, Leaflet and a dozen other clients with no further work by anyone. That interoperability is the entire value proposition, and it is why national mapping agencies and county governments run GeoServer rather than bespoke APIs.

The object model

  • Workspace — a namespace grouping related layers, e.g. kiambu.
  • Store — a connection to a data source: your PostGIS database, a directory of GeoTIFFs.
  • Layer — one publishable table or coverage from a store.
  • Layer group — several layers served as one, in a fixed draw order.
  • Style — an SLD document describing how a layer is drawn.

Three services, three jobs

ServiceReturnsUse for
WMSA rendered image of the requested areaComplex cartography, large datasets, styling controlled server-side. The client cannot interrogate the features.
WFSThe actual features, as GML or GeoJSONWhen the client needs the geometry and attributes — to analyse, restyle, or edit. Heavier.
WMTSPre-rendered tiles on a fixed gridBase maps and any layer that changes rarely. Cacheable, so much faster than WMS.

The decision is nearly always: does the browser need the geometry? If it only needs to look at it, WMS or WMTS — the server does the drawing and sends pixels, and a million-feature layer costs the same as a hundred-feature one. If the user must click a feature and get its attributes, or you want to restyle without a server round trip, WFS or your own GeoJSON API.

Every OGC service answers a GetCapabilities request with an XML document listing what it offers: layer names, titles, supported coordinate systems, bounding boxes, available formats, and the operations it supports. It is a machine-readable contract, and it is how QGIS populates its layer list when you paste in a WMS URL.

SLD in one page

Styled Layer Descriptor is the OGC's XML styling language. It is verbose, and it is also a genuine standard that transfers between servers. The structure is a set of rules, each with an optional filter and one or more symbolizers.

XML 
<Rule>
  <Name>Level 4 and above</Name>
  <ogc:Filter>
    <ogc:PropertyIsGreaterThanOrEqualTo>
      <ogc:PropertyName>level</ogc:PropertyName>
      <ogc:Literal>4</ogc:Literal>
    </ogc:PropertyIsGreaterThanOrEqualTo>
  </ogc:Filter>
  <PointSymbolizer>
    <Graphic>
      <Mark>
        <WellKnownName>circle</WellKnownName>
        <Fill><CssParameter name="fill">#0E6E78</CssParameter></Fill>
      </Mark>
      <Size>12</Size>
    </Graphic>
  </PointSymbolizer>
</Rule>

Rules can also carry MinScaleDenominator and MaxScaleDenominator, which is how a layer shows only labels at small scales and full symbology at large ones. Writing SLD by hand is tedious; generate a first version by styling the layer in QGIS and exporting as SLD, then edit. That is standard professional practice, not a shortcut.

CORS: why it works on your machine and fails when deployed

WMS layers are loaded as images, and images are exempt from the cross-origin rule — so a WMS layer usually works everywhere. WFS returns JSON, which your JavaScript must read, and reading a cross-origin response requires the server's permission.

If your page is served from example.com and GeoServer runs on gis.example.com:8080, those are different origins, and the browser blocks the WFS response unless GeoServer sends Access-Control-Allow-Origin. It works in the lab because both are on localhost. The symptom is a Console message naming CORS explicitly and a Network tab showing the request succeeded with status 200 — the data arrived, and the browser refused to hand it to your code. The fix is on the server: enable GeoServer's CORS filter, or put both behind one reverse proxy so there is only one origin.

Caching

GeoServer bundles GeoWebCache, which stores rendered tiles so that repeat requests are served as files rather than re-rendered. For any layer that changes less often than it is viewed — which is nearly all base data — this is the difference between a map that feels instant and one that does not. Seed the cache for the zoom levels you actually serve, and remember to invalidate it when the underlying data changes, because a stale tile cache is a genuinely confusing bug: the database is right and the map is wrong.

Validate twice

Client-side validation is for the user: fast feedback, no wasted round trip. Server-side validation is for correctness, because anything a browser can send, an attacker can send without using a browser. Disabling a submit button prevents nothing — curl does not run your JavaScript. Every rule that must hold has to be enforced on the server; the client copy is a convenience.

For spatial data specifically, check: the geometry is the type you expected; it is valid (ST_IsValid); it falls inside your area of interest; polygons are not absurdly large or self-intersecting; and the vertex count is bounded, or someone will post a polygon with a million points.

SQL injection, and the one habit that prevents it

Never build SQL by string formatting with values that came from a user. This is not a stylistic preference.

# CATASTROPHIC — the user controls your SQL
cur.execute(f"SELECT * FROM reports WHERE category = '{cat}'")

# A category of:  x' OR '1'='1
#   returns every row, including rows the user should never see.

# CORRECT — the driver sends the value separately from the statement
cur.execute("SELECT * FROM reports WHERE category = %s", (cat,))

With a parameterised query the value can never be parsed as SQL, whatever it contains. The habit to build is simple and absolute: if a value came from outside your program, it goes in the parameter tuple, never in the string. This applies to ORDER BY columns and table names too — those cannot be parameterised, so validate them against an allow-list of permitted names instead.

Secrets

Anything in your JavaScript is public. Not "hard to find" — public: it is delivered to every visitor and readable with two clicks. Database passwords, API keys with billing attached, and admin tokens must live in server-side environment variables, never in client code and never committed to git.

Where a third-party key must be used from the browser — some tile providers require this — restrict it at the provider: lock it to your domain, cap the request rate, and set a spending limit. Treat a leaked key as a bill you will personally receive, because that is how it usually presents.

Authentication, in the amount this unit needs

You are not building a production identity system. You do need to understand the shape: authentication establishes who a user is; authorisation decides what they may do. Store password hashes, never passwords — use a library, never your own hashing. Serve everything over HTTPS, because a session cookie sent over plain HTTP is readable by anyone on the same network. And check authorisation on the server for every write, on every request; hiding a delete button is presentation, not security.

Measure before you optimise

Open the Network tab, hard-reload, and record three numbers: total bytes transferred, number of requests, and time until the map is usable. Then throttle the connection to "Slow 3G" and record them again. That second set is the real number for a large share of your users.

This is not an abstract concern in Kenya. Most users reach your map on a phone, over mobile data bought in bundles. A 40 MB GeoJSON is not merely slow — it consumes a measurable fraction of a monthly bundle to display one screen, and the user pays for the 39 MB they never see. A map that is expensive to open is a map that does not get opened. Payload is a design constraint, not a technicality, and it belongs in your project's requirements alongside the cartography.

Vector tiles

A vector tile is the same tile pyramid idea applied to geometry instead of pixels: each tile holds the features intersecting it, clipped, simplified to that zoom, and encoded compactly as protobuf (the MVT format). The browser draws them.

Compared with GeoJSON: only the visible area is transferred; each zoom gets appropriately generalised geometry; the encoding is far denser than JSON text; and styling stays client-side, so you can restyle instantly without re-fetching. Compared with raster tiles: features remain interactive and restylable, and the tiles are usually smaller.

The cost is complexity — you need something to generate and serve them (tippecanoe to build, pg_tileserv or ST_AsMVT to serve dynamically) and MapLibre GL rather than plain Leaflet to get the full benefit. The rule of thumb: under a few thousand features, GeoJSON with bbox filtering is simpler and fine. Above roughly ten thousand, vector tiles.

SQL 
-- vector tiles straight from PostGIS, no tile server needed
WITH bounds AS (SELECT ST_TileEnvelope(%(z)s, %(x)s, %(y)s) AS geom),
     mvtgeom AS (
  SELECT ST_AsMVTGeom(ST_Transform(f.geom, 3857), bounds.geom) AS geom,
         f.id, f.name, f.level
  FROM facilities f, bounds
  WHERE ST_Intersects(ST_Transform(f.geom, 3857), bounds.geom)
)
SELECT ST_AsMVT(mvtgeom, 'facilities') FROM mvtgeom;

Cloud-native: the range request

One idea underlies the whole cloud-native geospatial movement. HTTP lets a client request part of a file — a byte range — rather than the whole thing. So if a file is organised so that its useful pieces sit in known places, a client can read just the pieces it needs, straight from cheap static storage, with no server-side software at all.

  • COG — Cloud-Optimised GeoTIFF. A GeoTIFF internally tiled with overviews, and an index at the front. A client reads the header, works out which byte ranges hold the tiles it needs, and fetches only those. A 5 GB satellite scene becomes usable over the web without downloading it.
  • PMTiles. An entire tile pyramid in a single file with an embedded directory. The client range-requests individual tiles. No tile server, no database — a static file on any web host. For a base map that changes rarely this is a strikingly good answer, and it removes an entire class of operational work.
  • STAC. A JSON standard for cataloguing spatiotemporal assets, so a client can search "Sentinel-2 over Kiambu, June 2026, under 10% cloud" and get back COG URLs.

When you do not need GeoServer. You have learned it, and it is genuinely the right tool for OGC interoperability, complex server-side styling, and datasets that change constantly.

But if your data is static and you want a fast base map, PMTiles on static hosting will outperform it at a fraction of the operational cost — nothing to patch, nothing to restart, nothing to run out of memory at 3 a.m. Knowing when not to deploy the heavy tool is a professional judgement, and it is one this unit expects you to be able to make and justify.

Getting it online

Two routes, and the choice follows from what you built.

  • Static hosting — GitHub Pages, Netlify, Cloudflare Pages. If your map is HTML, CSS, JavaScript and data files with no server-side code, this is free, fast, HTTPS by default, and needs no maintenance. It cannot run your Flask API.
  • A virtual private server — a small Linux machine you administer. Required once you have a database and an API. You install and maintain everything, and the machine is yours to secure.

On a VPS the pieces are: a WSGI server (gunicorn) running your Flask app; a reverse proxy (nginx) in front of it serving static files and terminating TLS; PostgreSQL; and a certificate from Let's Encrypt via certbot, which is free and automatic. Configuration lives in environment variables, never in the repository. Docker Compose is worth the afternoon it takes to learn, because it turns that whole stack into one file that runs identically on your laptop and the server — which is what makes "it worked on my machine" stop being a sentence you say.

HTTPS is not optional. Browsers restrict features on insecure origins — geolocation, among others, simply does not work over plain HTTP — and any credential sent over HTTP is readable by everyone between the user and your server.

OpenStreetMap

OSM is a free, editable map of the world built by volunteers. Its data model has three primitives and one organising idea:

  • Node — a point with a coordinate. May carry tags, or exist only as part of a way.
  • Way — an ordered list of nodes. Open for a road, closed for a building.
  • Relation — an ordered list of members with roles: a bus route, a multipolygon with holes, an administrative boundary.
  • Tags — free-form key/value pairs on any element. There is no fixed schema; conventions are documented on the wiki and enforced only by community agreement, which is both OSM's flexibility and its main data-quality problem.
The ODbL follows your data

OSM data is licensed under the Open Database Licence. Two obligations matter. Attribution — credit OpenStreetMap contributors visibly. Share-alike — if you publish a derived database, you must publish it under the ODbL too.

The consequential subtlety is what counts as "derived". Producing a map image from OSM is a produced work, which needs attribution but not share-alike. Merging OSM geometry into your own database and publishing that is a derivative database, and share-alike bites. Students frequently plan a commercial project on OSM data without noticing that they may be obliged to open their database. Check before you build, not after.

Volunteered geographic information

Goodchild's phrase "citizens as sensors" named a genuine shift: the people who know a place best now have the tools to map it. The results can be extraordinary. Humanitarian OpenStreetMap Team mobilises remote volunteers to trace buildings and roads from imagery within hours of a disaster, and that data has routed real responders. Map Kibera, begun in 2009, is the case worth studying closely: Kibera appeared on official maps as a blank space, and residents mapped their own settlement — schools, clinics, water points, toilets — producing data that was used in service planning and advocacy. The people mapping were the people mapped.

Quality is the standing question. VGI has no formal accuracy specification and no accountable producer. In practice it is uneven in a predictable way: excellent where many contributors are active, thin where few are. Assess it as you would any dataset — check completeness against an independent source, look at edit history and contributor count, compare geometry against recent imagery, and be explicit in your report about what you checked. "It came from OSM" is a provenance statement, not a quality statement.

The ethics, which are not optional in this unit

A map is an intervention. It makes some things visible and leaves others out, and both have consequences for real people. Four issues arise directly in the projects you are building.

Locational privacy

A person's location over time is among the most sensitive data there is. It reveals where they live, work, worship, seek medical care, and who they associate with. Aggregate before publishing, coarsen precision, and think hard before mapping individuals at all. Note that de-identification is weaker than it looks: a "de-identified" set of home locations is trivially re-identifiable, because a home location is an identifier.

Mapping vulnerable people

Publishing precise locations of a group can expose them to targeting. This is not hypothetical: locations of refugees, of people receiving HIV care, of survivors of violence, of undocumented residents, of rhino populations. The rule is to ask who else can read this map and what they might do with it. Sometimes the correct professional decision is a coarser map, or no map.

Consent and benefit

If you map a community, did they agree, and do they gain? The distinction between mapping with a community and mapping it as a subject is the distinction between Map Kibera and extraction. This applies to student projects too: the residents whose settlement you map for coursework are not a dataset.

Absence is a decision

What a map omits shapes what gets funded and served. A settlement absent from official maps is absent from planning. Choosing what to include, and at what resolution, is an exercise of power, and pretending it is a neutral technical choice is itself a choice.

What a finished project looks like

Not "it runs on my laptop". A finished web mapping project has: a public URL over HTTPS; a README that a stranger can follow to a running instance; data whose source and licence are stated; secrets outside the repository; sensible behaviour when the network is slow or the API is down; and a map that is legible on a phone.

Reviewing code

Six things that will actually bite you

  • this in JavaScript. It means different things in different call contexts. Arrow functions inherit this from where they were written, which is nearly always what you want — prefer them in callbacks.
  • == versus ===. The double equals coerces types, so "" == 0 is true and null == undefined is true. Use === always, without exception.
  • Everything asynchronous is asynchronous. If a value is undefined right after a fetch, nothing is broken — the fetch has not finished. Week 2 covers this properly.
  • SQL is declarative. You describe the result you want; the planner decides how to get it. Do not write loops in SQL. If you are reaching for a cursor, you are usually one JOIN or one window function away from the right answer.
  • NULL is not a value. NULL = NULL is not true, it is NULL. Use IS NULL. This bites in outer joins, where the absent side is all nulls.
  • Semicolons and braces. JavaScript will insert semicolons for you in ways that occasionally surprise. Use a formatter — Prettier is one click in VS Code — and stop thinking about it.
